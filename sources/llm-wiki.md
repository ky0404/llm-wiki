# LLM Wiki 核心概念摘要

## 核心要点

LLM Wiki 是一种基于编译增强生成（CAG）的个人知识库构建模式，与传统 RAG（检索增强生成）有本质区别。核心思想是让 LLM 增量构建和维护一个持久化的 wiki，而不是每次查询时从原始文档重新检索。

### 关键区别：CAG vs RAG
- **RAG（传统方式）**：每次查询时从原始文档检索相关片段，LLM 需要重新发现知识
- **CAG（LLM Wiki 方式）**：LLM 构建和维护一个结构化的 wiki，知识被编译一次并保持更新

### 核心优势
1. **持久化、复合的产物**：wiki 随着每个新源的添加和每个问题的提出而不断丰富
2. **交叉引用已存在**：矛盾已被标记，综合已反映所有阅读内容
3. **维护成本接近零**：LLM 不感到无聊，不会忘记更新交叉引用，可以一次处理 15 个文件

## 架构
### 三层结构
1. **原始源**（Raw sources）：不可变的源文档集合，是真理的来源
2. **Wiki**：LLM 生成的 markdown 文件目录，LLM 完全拥有这一层
3. **模式**（Schema）：告诉 LLM wiki 如何结构化、约定是什么、工作流程如何的文档（如 CLAUDE.md 或 AGENTS.md）

### 操作流程
#### 1. 摄入（Ingest）
- 将新源放入原始集合
- LLM 处理源文件，讨论关键要点
- 在 wiki 中编写摘要页
- 更新索引和相关实体/概念页面
- 追加日志条目

#### 2. 查询（Query）
- 向 wiki 提问
- LLM 搜索相关页面，读取并综合答案
- 答案可以归档回 wiki 作为新页面
- 探索结果在知识库中复合，就像摄入的源一样

#### 3. 健康检查（Lint）
- 定期检查 wiki 健康状况
- 查找：页面间的矛盾、过时的声明、孤立页面、缺少的交叉引用、数据缺口
- LLM 擅长建议新问题调查和新源查找

## 索引和日志
### index.md
- 内容导向的目录
- 列出 wiki 中的每个页面，包含链接、一行摘要和可选元数据
- 按类别组织（实体、概念、源等）
- LLM 在每次摄入时更新

### log.md
- 按时间顺序的记录
- 仅追加的记录，记录发生了什么和何时发生
- 每个条目以一致的前缀开始（如 `## [2026-04-02] ingest | Article Title`）
- 提供 wiki 演化的时间线

## 工具和技巧
### 推荐工具
- **Obsidian Web Clipper**：将网页文章转换为 markdown
- **Obsidian 图形视图**：查看 wiki 形状的最佳方式
- **Marp**：基于 markdown 的幻灯片格式
- **Dataview**：在页面 frontmatter 上运行查询的 Obsidian 插件
- **qmd**：本地 markdown 文件搜索引擎，具有混合 BM25/向量搜索和 LLM 重新排名

### 图像处理技巧
- 将图像下载到本地磁盘
- LLM 无法原生一次性读取带有内联图像的 markdown
- 解决方法：让 LLM 先读取文本，然后单独查看部分或所有引用的图像

## 应用场景
1. **个人**：跟踪目标、健康、心理、自我提升
2. **研究**：深入某个主题数周或数月
3. **阅读书籍**：逐章归档，构建角色、主题、情节线的页面
4. **业务/团队**：由 LLM 维护的内部 wiki
5. **竞争分析、尽职调查、旅行规划、课程笔记、爱好深入**等

## 为什么有效
- 维护知识库的繁琐部分不是阅读或思考，而是簿记
- 人类放弃 wiki 是因为维护负担增长快于价值
- LLM 不感到无聊，不会忘记更新交叉引用
- 人类的职责是策划源、指导分析、提出好问题、思考其意义
- LLM 的职责是其他一切

## 历史渊源
这个想法在精神上与 Vannevar Bush 的 Memex（1945）相关——一个私人的、精心策划的知识存储，文档之间有联想路径。Bush 的愿景更接近这个，而不是网络变成的样子：私人的、积极策划的，文档之间的连接与文档本身一样有价值。他无法解决的部分是谁来做维护工作。LLM 处理这一点。
