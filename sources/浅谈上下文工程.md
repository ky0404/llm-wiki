## 核心要点
本文探讨了从提示工程到上下文工程的转变，并分析了 Claude Code、Manus 和 Kiro 等产品的实践。
- **上下文工程定义**：构建动态系统，以合适的格式为大语言模型提供正确的信息和工具，让其合理完成任务。上下文不仅指单一提示词，更是模型在生成响应前看到的一切信息。
- **组成部分**：指令/系统提示词、用户提示词、当前状态/对话历史（短期记忆）、长期记忆、检索的信息（RAG）、可用工具、结构化输出。
- **提示工程 vs 上下文工程**：前者关注词句技巧，后者关注提供全面上下文（文档、示例、规则、模式、验证）。
- **长上下文的 Context-Rot 问题**：随着上下文长度增加，模型注意力可能出现“腐蚀”。解决方案包括 Offload（卸载）、Retrieve（检索）、Reduce（压缩）、Isolate（隔离）。
- **LangChain 的上下文管理方法论**：写入（文件系统、记忆、数据库）、选择（RAG、文本检索）、压缩（摘要、Rerank）、隔离（环境隔离、多 Agent 分离）。
- **Claude Code 的工程实践**：
  - 三层记忆架构（短期、中期智能压缩、长期 CLAUDE.md）。
  - 实时 Steering 机制（异步消息队列 + 主循环）。
  - 分层多 Agent 协作（主 Agent 协调 + SubAgent 执行）。
  - 动态上下文注入（自动识别和注入相关文件内容）。
- **Manus 的优化实践**：
  - 围绕 KV 缓存设计，保持前缀稳定，上下文只追加。
  - 遮蔽而非移除工具，保持上下文稳定性。
  - 使用文件系统作为终极上下文。
  - 通过复述待办事项列表操控注意力，避免“丢失在中间”问题。
  - 保留错误内容，让模型从失败中学习。
- **Spec-Driven Development**：从 Vibe Coding（Prompt → Code）转向规范驱动（Prompt → Requirements → Design → Tasks → Code），Kiro 采用此模式。
- **未来展望**：从上下文工程走向环境工程，构建持续演化、可感知、可交互的智能环境。
