# LLM 编码最佳实践

## 定义
LLM 编码最佳实践是一套指导原则，旨在解决 LLM 在代码生成和维护中的常见问题，提高代码质量和开发效率。

## 核心问题
LLM 编码存在以下常见问题：
1. **错误假设**：默默做出假设而不寻求澄清
2. **隐藏困惑**：不管理自身的不确定性
3. **过度工程**：创建不必要的复杂性和抽象
4. **无关修改**：改动或删除不理解的相关代码
5. **缺乏验证**：没有明确成功标准就执行

## 解决方案框架
基于 [[sources/CLAUDE]] 的四个原则：

### 1. 编码前思考
- **明确假设**：陈述所有假设，如果不确定就提问
- **呈现权衡**：当存在多种解释时，展示所有选项
- **适时反对**：如果存在更简单的方法，说出来
- **管理困惑**：遇到不清楚的地方就停下来要求澄清

### 2. 简洁优先
- **最小代码**：用最少的代码解决问题
- **避免推测**：不添加未要求的功能或抽象
- **简化检查**："资深工程师会觉得这过于复杂吗？"
- **重写原则**：如果 200 行能写成 50 行，就重写

### 3. 精准修改
- **最小接触**：只修改必须修改的部分
- **保持原样**：不"改进"相邻代码、注释或格式
- **风格一致**：匹配现有风格，即使个人偏好不同
- **清理责任**：只清理自己造成的混乱

### 4. 目标驱动执行
- **定义标准**：将任务转化为可验证的目标
- **验证循环**：循环执行直到达成目标
- **计划明确**：对于多步骤任务，提供清晰的验证计划

## 实施指南
### 检验标准
- **每一行修改**：都应该能直接追溯到用户的请求
- **过度复杂检查**：资深工程师会觉得这过于复杂吗？
- **必要性检查**：这个抽象/功能/错误处理真的必要吗？

### 权衡管理
指南倾向于**谨慎而非速度**：
- **琐碎任务**：自行判断，不需要完整的严谨流程
- **非琐碎工作**：遵循完整指南以减少代价高昂的错误
- **目标**：减少错误，而不是拖慢简单任务

## 效果指标
指南生效的标志：
1. **更少的无关修改**：diff 中只出现请求的改动
2. **更少的重写**：代码第一次就写得简洁
3. **提前澄清**：澄清问题在实现之前提出
4. **干净的 PR**：没有顺带的重构或"改进"
